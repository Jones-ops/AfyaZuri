# Backup and restore

The embedded PostgreSQL that Afyazuri ships has no `pg_dump`, so Afyazuri has its own backup tool (`apps/api/src/ops/backup.js`). It:

1. opens one **REPEATABLE READ** snapshot, so every table is captured as of the same moment, while clinical work carries on;
2. streams each table with PostgreSQL `COPY`;
3. compresses with gzip and encrypts with **AES-256-GCM** using `BACKUP_KEY`;
4. writes `afyazuri-YYYYMMDD-HHMMSS.azb` (the name is in UTC), then immediately re-reads it to verify.

The GCM tag makes the file **tamper-evident**. A modified file, or the wrong key, is rejected before anything is restored.

> The data inside is still encrypted where Afyazuri encrypts fields. A restore needs the same `ENCRYPTION_KEY` and `BLIND_INDEX_KEY` as the source system, as well as `BACKUP_KEY`.

## Automatic nightly backups

Set these in `.env` and restart:

```ini
BACKUP_KEY=...            # generated by npm run secrets
BACKUP_DIR=backups
BACKUP_OFFSITE_DIR=E:/afyazuri-backups   # optional second copy: USB disk, NAS or network share
BACKUP_CRON=30 1 * * *    # 01:30 Nairobi time (default)
BACKUP_KEEP_DAILY=7
BACKUP_KEEP_WEEKLY=4
BACKUP_KEEP_MONTHLY=12
```

The API's job runner (pg-boss) then creates and verifies a backup every night, applies the retention policy and copies the file off-site. Results appear in the logs as `backup.nightly complete`.

**Retention** keeps the newest backup from each of the last 7 days, the last 4 ISO weeks and the last 12 months, which is at most 23 files. Everything else is deleted, in `BACKUP_DIR` and in `BACKUP_OFFSITE_DIR` alike.

## Manual commands

```bash
npm run backup                                   # back up now, verify, prune, copy off-site
npm run backup -- verify backups/afyazuri-20261116-223000.azb
npm run backup -- prune
```

`verify` decrypts the whole file and checks every table without touching any database:

```
✓ afyazuri-20261116-223000.azb is intact
  created 2026-11-16T22:30:00.000Z from database "afyazuri"
  46 tables, 796 rows, 7 migrations
```

## Restoring

Restore **replaces everything** in the target database. Always rehearse on a scratch database first.

```bash
# 1. Rehearse: restore into a new, empty database and check it
npm run backup -- restore backups/afyazuri-20261116-223000.azb \
  --database-url postgres://postgres:<PG_PASSWORD>@localhost:54329/afyazuri_restore_test --yes

# 2. For real: stop Afyazuri, restore into the live database, start Afyazuri
npm run backup -- restore backups/afyazuri-20261116-223000.azb \
  --database-url postgres://postgres:<PG_PASSWORD>@localhost:54329/afyazuri --yes
```

The target database must exist. With the embedded server, create one using any PostgreSQL client, or run `CREATE DATABASE afyazuri_restore_test;` through the restore user.

What restore does:

1. Verifies the whole file (tag and structure). Nothing is changed if this fails.
2. Drops and recreates the `public` schema, then runs this version's migrations. The migration list must match the backup's, so restore with the **same Afyazuri version** that took the backup, then upgrade.
3. Loads all rows in one transaction with triggers disabled (`session_replication_role = replica`), so append-only guards and change capture don't fire for historic rows.
4. Moves every sequence past the restored rows and commits. Triggers are active again afterwards. The audit log is append-only again immediately, and the tests check this.

**Privileges:** step 3 needs a superuser, which the embedded server's `postgres` user is. On managed PostgreSQL without superuser, use the provider's own snapshot or restore features for disaster recovery, and use Afyazuri backups as an additional portable copy.

## Restore drill (do this quarterly)

1. Copy last night's file from the **off-site** location, not the server.
2. On any machine with Node.js and the Afyazuri code at the same version: `npm ci`, put the three keys in `.env`, then run `npm run db:local`.
3. Create a scratch database, run the restore command above against it, then run `npm start` with `EXTERNAL_DATABASE_URL` pointing at that scratch database and sign in.
4. Note how long it took and record the drill (date, file, who, outcome).

## Point-in-time recovery

Logical nightly backups can lose up to a day of data. Where that is too much, for example in cloud deployments, run a separately managed PostgreSQL 16 with WAL archiving and point-in-time recovery (most managed services enable it by default), and connect Afyazuri to it with `EXTERNAL_DATABASE_URL`.
